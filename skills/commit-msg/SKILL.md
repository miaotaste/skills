# 提交信息

本技能只起草提交信息。用户没有明确说「执行提交」时，不要运行 `git commit`。

Conventional Commit 类型、scope、文件名和代码符号保留原始形式，不翻译。

## 工作流程

1. 先运行 `git log -20 --format=%s`。emoji、说明语言、scope 用词跟随近期提交。没有历史时，默认中文，并加上类型 emoji。
2. 只分析已暂存的变更。按需运行 `git status --short`、`git diff --cached --stat`、`git diff --cached --name-only`，对重要文件运行 `git diff --cached -- <path>`。变更较大时用 `git diff --cached --unified=0` 定位函数、常量和测试。
3. 不得根据未暂存或未跟踪的文件推断提交内容。
4. 按下面的类型和 scope 规则起草，再用「输出」一节的格式给出结果。

## 类型

只按这三条判断，不靠某一个界面上的例子：

- 用户以前不能单独完成的能力，用 `feat`。
- 既有行为的结构调整、样式、文案、布局，用 `refactor`。
- 明确的缺陷或回归，用 `fix`。

没有历史提交时，类型 emoji 为：`feat` → `✨`，`fix` → `🐛`，`refactor` → `🔧`。近期提交没有 emoji 时，不要给新提交加上 emoji。

接口或行为不兼容时，在类型后加 `!`，正文最后一行写 `BREAKING CHANGE:` 和说明。

## Scope

scope 只来自当前仓库：上一步的 `git log -20 --format=%s`，以及现有包名、目录名。

业务范围和技术范围仍要区分：

- 产品流程、领域对象、用户可见行为或业务规则发生变化时，用业务范围。实现跨了 API、数据库、文案或测试，只要它们服务于同一个产品变更，仍然用业务范围。
- 共享基础设施、构建、依赖、框架接入或内部机制本身是变更主题时，用技术范围。

沿用本仓库已经出现过的 scope；没有就省略。不要编造仓库里没出现过的 scope，也不要把包名和领域名拼成新标签。变更跨了多个领域且没有明确归属时，同样省略 scope。

## 标题与要点

标题聚焦结果，优先一句话，不罗列文件，不用「更新代码」或「修复问题」。

有行为变化时，在标题下列出要点：用「新增」「统一」「移除」「补充」「调整」开头，用反引号标出文件、模块或符号，说明行为或结构为什么变。避免「修改了很多文件」「优化代码」「修复 bug」。

单文件且行为不变时只写标题，不写要点。

## 输出

默认只输出一个围栏代码块：

```text
<emoji> type(scope): 提交标题

- 变更要点
```

emoji 是否出现、说明用哪种语言、scope 用哪个词，都跟随近期提交。没有历史时用中文和类型 emoji。scope 可以省略。单文件且行为不变时，代码块里只有标题。破坏性变更写成 `type!(scope):`，代码块最后一行是 `BREAKING CHANGE:`。

只有下面三种情况才在代码块外写两三句，不要附翻译：

- 暂存区是空的：请用户先暂存要提交的文件，不要编造提交信息。
- 看不到 diff：请用户提供 `git diff --cached`、补丁，或已暂存文件的摘要。只根据用户给出的材料起草，不猜测。
- 变更应该拆开：说明原因，并建议拆开。

输出前确认文字与暂存差异一致，不编造文件或行为。
