# 提交信息

适用于用户希望提交信息像简洁的变更日志一样，包含标题和变更要点的场景。

## 目标

生成以下风格的提交信息：

```text
✨ feat(scope): 提交摘要

- 变更点 1，尽量点名文件、模块或符号
- 变更点 2，描述用户可感知的行为或结构调整
- 变更点 3，补充测试、清理或迁移信息
```

仅输出提交信息。Conventional Commit 类型、scope、文件名和代码符号保留原始形式。

## 工作流程

1. 检查仓库状态。
2. 仅分析已暂存的变更。
3. 将相关修改归纳为 3–7 条有意义的要点。
4. 选择最合适的 Conventional Commit 类型，并判断可选的 scope 应采用业务范围还是技术范围。
5. 根据提交类型选择对应的 emoji。
6. 用标题概括整体意图，避免罗列文件。

## 检查变更

按需运行最少量的命令：

- `git status --short`
- `git diff --cached --stat`
- `git diff --cached --name-only`
- 对重要文件运行 `git diff --cached -- <path>`

变更较大时，使用 `git diff --cached --unified=0` 快速定位修改的函数、常量和测试。

不得根据未暂存或未跟踪的文件推断提交内容。
没有已暂存的变更时，停止生成，并请用户先暂存希望提交的文件。

## 选择标题

根据变更对用户的实际意义选择 Conventional Commit 类型，而不是仅看是否修改了 UI 文件：

- `feat` → `✨`：新增用户可见的能力、工作流程、路由、入口、权限、数据展示或业务行为。
- `fix` → `🐛`：修复缺陷、回归问题、错误数据或兼容性问题。
- `refactor` → `🔧`：内部结构调整、UI 或布局优化、文案整理、样式统一、加载状态对齐、组件重组，或有测试支持的既有行为整理，且没有新增能力。
- `perf` → `⚡️`：可衡量的性能提升。
- `test` → `✅`：新增或更新测试，且未改变生产逻辑。
- `docs` → `📝`：仅修改文档。
- `build` → `📦`：依赖、构建、CI 或工具链接入变更。
- `chore` → `🧹`：不适合归入其他类型的维护工作。

选择 `feat` 前，按以下规则处理容易混淆的情况：

- 对现有页面或组件进行重新设计、样式调整、文案修改、位置调整或对齐时，优先使用 `refactor`，即使结果对用户可见。
- 在现有 UI 中移动信息、统一胶囊标签或徽章及加载样式、修改标签、移除装饰元素或简化组件结构时，优先使用 `refactor`。
- 改善现有页面或组件内的交互，主要涉及导航、滚动、对齐、响应式布局、信息密度或操作提示，且未新增产品流程时，优先使用 `refactor`。例如点击分区标题滚动到同一视图内的位置、重新计算时间轴或表格宽度、对齐吸顶区域、移除冗余摘要标签。
- 不因新增点击处理、键盘或 ARIA 支持、可见交互就选择 `feat`。仅当交互带来超出现有视图的独立用户能力时使用 `feat`，例如新增流程、路由、弹窗任务、筛选器、由 API 提供的数据展示或领域行为。
- 同一既有页面的暂存变更同时包含交互优化和小型视觉缺陷修复时，如果主要意图是组件或布局重组，且数据、权限、API 和业务规则均无错误，优先使用 `refactor`。
- 仅当暂存变更增加了用户此前无法独立完成或查看的能力时使用 `feat`，例如新页面、操作、筛选器、弹窗流程、由 API 提供的数据展示或业务规则。
- 明确纠正损坏、误导、不可访问或非预期行为时，使用 `fix` 而不是 `refactor`。除非差异或用户请求明确指出缺陷或回归问题，否则视觉整理不算 `fix`。
- 仅用于保障生产代码重构行为的测试更新，应沿用生产代码的提交类型；只有测试是唯一有意义的暂存变更时才选择 `test`。

标题必须以所选类型对应的 emoji 开头，不得省略。

变更主要属于一个明确、真实的产品领域、包、应用、服务或模块时，添加 scope，例如 `feat(coach)` 或 `fix(auth)`。

根据暂存内容选择 scope 的方向，而不是根据差异中的第一个路径：

| 范围方向 | 适用场景 | scope 示例 |
| --- | --- | --- |
| 业务范围 | 产品流程、领域对象、用户可见行为或业务规则发生变化 | `order`, `payment`, `coupon`, `recommendation`, `coach`, `admin`, `user`, `session`, `schedule`, `bay` |
| 技术范围 | 共享基础设施、构建工具、依赖、框架接入、底层工具或内部机制发生变化 | `ui`, `utils`, `api`, `service`, `auth`, `db`, `i18n`, `deps`, `build`, `ci`, `types`, `config` |

- 暂存变更主要修改产品流程、领域对象、用户可见行为或业务规则时，使用业务范围。
- 即使实现跨越 API 处理函数、服务、数据库结构、共享查询 Hook、i18n 字典、模拟数据或测试，只要这些修改服务于同一个产品或领域变更，仍使用业务范围。
- 暂存变更主要修改共享基础设施、构建工具、依赖、框架接入、底层工具、跨领域技术行为或不属于单一产品领域的内部机制时，使用技术范围。
- 只有 API 或服务层本身是修改主题时，才使用 `api` 或 `service` 等技术范围，例如中间件、请求解析、客户端接入、路由清单或服务抽取。如果处理函数或服务的修改是为了实现某个产品或领域行为，则使用业务范围。
- 混合提交选择对外有意义的主要归属领域。如果业务和技术变更互不相关或同等重要，省略 scope，并在回复中说明这些变更的划分。
- 不创建 `coach-api`、`admin-ui` 或 `payment-service` 等混合 scope；根据主要意图选择业务范围或技术范围。

示例：

- `feat(order): 新增预订流程`
- `fix(payment): 重试超时回调`
- `build(turbo): 优化缓存`
- `chore(deps): 升级 React`

路径仅是实现细节时，优先使用团队讨论该变更时会采用的领域名称，而不是原始路径名称。
变更明确属于某个产品领域，且 API、类型、数据库、i18n 或测试中的修改仅提供支持时，使用该产品领域作为 scope。
优先使用简洁的产品范围，例如：

- 教师或教练流程使用 `coach`，即使暂存文件跨越 `apps/coach-app`、教练 API 类型或 Hook、API 处理函数、数据库支持、i18n、模拟数据或测试。
- 组织或教室管理流程使用 `admin`，即使支持文件位于 `apps/admin-app` 之外。
- 学生或会员流程使用 `user`，即使支持文件位于 `apps/user-app` 之外。

变更主要属于共享技术领域，而不是某个产品流程时，使用 `auth`、`db`、`i18n`、`api` 或包名、模块名等技术范围。
当 `coach`、`admin` 或 `user` 更能表达业务范围时，不保留 `coach-app`、`admin-app` 或 `user-app` 等包名后缀。
如果只能编造一个 scope 标签，例如路径、模块或产品术语中都没有出现的功能主题，则省略 scope。
变更跨越多个领域且没有明确归属时，也省略 scope。

标题规则：

- 聚焦结果或主题。
- 优先使用一句话，避免用逗号拼接多个分句。
- 避免“更新代码”或“修复问题”等含糊标题。
- 不在标题中罗列所有文件。

## 编写变更要点

每条要点应能独立阅读，并解释一组相关变更。

优先采用以下写法：

- 使用“新增”“统一”“移除”“补充”“调整”等明确动词开头。
- 用反引号标出具体文件、模块、路由、组件或符号。
- 解释行为变化的原因或架构意图，而不仅描述编辑动作。

好的要点示例：

- `新增 \`config/responsive.ts\``，统一 mobile/tablet/desktop 断点与布局密度配置。
- `调整 \`AuthenticatedLayout\` 与 \`PageFrame\`` 的间距和主区高度，使平板布局与桌面端保持一致。
- `补充 \`AuthenticatedLayout\`` 侧栏默认折叠与持久化行为的测试，覆盖平板场景。

避免以下写法：

- `修改了很多文件`
- `优化代码`
- `修复 bug`

## 输出格式

### 默认格式

仅在一个围栏代码块中输出提交信息。

使用以下结构：

```text
<emoji> type(scope): 提交标题

- 变更要点 1
- 变更要点 2
- 变更要点 3
```

emoji 为必填项，不得省略。
将提交信息放在一个围栏代码块中，不附加翻译。

## 质量检查

输出前检查提交信息是否：

- 与实际差异一致。
- 没有编造文件或行为。
- 包含 3–7 条要点，除非变更确实很小。
- 在新增或更新测试时提及测试。
- 准确区分重构和新增功能。
- 选择与暂存变更主要意图一致的业务范围或技术范围。
- 仅在一个代码块中呈现提交信息。

如果差异包含互不相关的变更，应明确说明，并选择以下方式之一：

- 分别给出提交建议。
- 明确说明当前提交信息假定所有列出的变更属于同一次提交。

## 小型变更的简化格式

变更很小时，简化为：

```text
🐛 fix(scope): 简洁摘要

- 变更要点 1
- 变更要点 2
```

## 缺少上下文

无法查看差异时，请用户提供以下内容之一：

- `git diff --cached`
- 补丁文件。
- 已暂存文件的截图或摘要。

根据用户提供的上下文生成提交信息，不猜测变更内容。
