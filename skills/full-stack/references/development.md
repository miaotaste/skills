# 开发与数据

实现贯通前端、协议和持久化的业务流程时读取。应用与模块的默认边界见 [选型与架构](architecture.md)；云端发布顺序见 [部署与恢复](deployment.md)。

## 先走通一个业务流程

选取能验证核心需求的操作，例如创建一条库存记录、重新读取列表并修改数量。完成该操作的输入、校验、持久化和失败反馈后，再扩展类似功能。需要登录的系统把认证包含在闭环内；账号数量、角色与租户关系由产品需求决定，不沿用参考项目的单管理员模型。

先确定公开输入和输出，再实现用例、持久化与界面。应用目录见 [选型与架构](architecture.md)。不要先批量生成空模块、空领域层或所有候选基础设施。

本地配置提供不含真实凭据的示例，明确公开前端配置和服务端私有配置。生成本地配置的工具若确有需要，应保留已有文件，不能覆盖用户已配置的数据库或存储。端口、配置加载顺序和构建入口以目标项目为准。新项目的脚本名见 [默认名字与形状](defaults.md)。

## 契约与协议边界

- 公共输入用 Zod 等运行时 schema 校验，TypeScript 类型从同一契约推导。契约描述可传输的数据，不导出数据库表、ORM 实例或服务端私有字段。
- 服务端始终验证输入与权限；前端校验只改善反馈。公开响应显式选择允许字段，避免内部对象新增字段后被自动暴露。
- 用例表达业务错误，HTTP/MCP 等适配器映射状态与响应。多入口调用同一用例，避免每种协议复制一套业务规则；没有 Agent 接入需求时只实现所需 HTTP 接口。
- 需要接口文档时，让 schema 和操作说明成为生成源，并检查生成结果；只有字段类型不足以表达权限、错误和示例，不把手写多份文档称为同源。

浏览器会话可采用 Cookie，明确 Secure、HttpOnly、SameSite 和写请求的来源校验；跨域确有需要时再配置具体 Origin 和凭据策略。机器调用采用独立凭证与权限，不能让错误 Bearer 回退到 Cookie 获得另一种身份。已有认证系统优先复用。

修改凭据或撤销访问时，明确旧会话的失效规则。密码、令牌、签名 URL 和包含秘密的完整请求不进入日志、幂等记录或业务快照。认证操作不能无差别套用通用请求结果缓存。

## 数据一致性按操作设计

| 情况 | 实现重点 |
| --- | --- |
| 多个写入必须一起生效 | 使用同一数据库事务连接；跨模块通过绑定到该事务的业务能力协作，不在中途另从池中取连接 |
| 多人或多入口可能覆盖编辑 | 使用 revision 等乐观并发机制，在事务或原子更新中比较；冲突时保留用户草稿，重新读取后再决定如何合并 |
| 写请求可能因网络中断被重试 | 为同一次操作保留幂等身份，比较规范化输入并保存可重放结果；同键不同内容拒绝执行，不能每次重试生成新键 |
| 数据保存后必须可靠启动任务 | 使用可与业务事务共同提交的队列写入，或显式 outbox；不能假设独立队列提交会随数据库回滚 |
| 外部操作返回结果未知 | 先按原请求标识查询或恢复，区分失败与结果未知；付费、不可逆操作不盲目重提 |

只对有相应需求的操作增加 revision、幂等或队列机制，不给所有 CRUD 预先套上同一框架。服务层只依赖业务接口，由装配入口提供 Drizzle、存储和队列实现；事务中避免无关的长时间网络调用。

幂等和并发冲突解决不同问题。数据库内的幂等记录应与业务修改同事务提交；同键并发需要唯一约束、锁或等效原子机制，不能只靠应用层先查后写。对结果重放设计明确的身份作用域，防止跨用户读取其他人的结果。

## 文件和后台任务按需增加

有文件需求时，先确定永久存储、访问权限、上传限制和文件身份。默认考虑 TOS；数据库保存业务关系与稳定对象标识，临时签名地址和本机路径不是永久身份。

较大文件可采用“申请上传 → 直传 → 服务端确认”的流程：确认时核对实际对象、大小与类型；授权过期刷新同一次上传，传输失败恢复传输，确认失败恢复确认。需要不可变原件时，限制旧上传授权覆盖已确认对象的能力。

对象存储写入或复制不参与 PostgreSQL 回滚。为确认失败、重复确认和遗留对象明确恢复、对账或限定范围的清理方案；不宣称跨存储原子提交，也不能在确认永久保存前删除唯一成果。方案复杂度由文件的重要性与失败成本决定。

后台任务采用持久队列时，默认考虑 pg-boss，先核实所用版本是否支持需要的事务接入方式；否则选择 outbox 等显式方案。任务可重试、可取消，重复执行不重复产生业务副作用，重试有上限。API 与 worker 是否同进程由任务耗时、资源和独立扩容需求决定。

文件保存状态与后处理状态分开。媒体解析失败仍保留已保存原件；只有确实需要媒体处理才引入 FFmpeg/FFprobe，并设置任务超时、临时空间预算和清理责任，不复制固定容量。停机先停止接收新任务，再等待或取消运行任务，最后关闭队列和连接池。

## 数据库生命周期明确分离

| 操作 | 责任与约束 |
| --- | --- |
| 建库 | 本地可由开发工具显式创建；生产由受控资源准备完成，不让常驻应用持有建库权限 |
| 生成迁移 | Drizzle schema 描述目标结构，生成有意义名称的追加迁移；数据库特有约束可用经过验证的自定义 SQL |
| 执行迁移 | 使用独立入口，保留 SQL、元数据和执行记录；协调并发执行，发现历史不一致时停止，不重写已应用文件 |
| seed | 显式初始化必要数据，重复执行不覆盖已有账号、设置或业务记录；初始化秘密只提供给该次操作 |
| 启动应用 | 检查必需配置、结构与初始化状态，给出明确错误；不隐式执行迁移或重置数据 |

数据库变更同时考虑已有数据和旧应用兼容性。已有项目不得通过清库解决结构冲突；需要删除、改名或收紧约束时，规划数据迁移和兼容窗口。不能把某个新项目不需要历史兼容的决定推广为通用规则。

涉及数据、并发或恢复的行为必须用相应层级验证，尤其是部分失败与重复执行，参见 [验证与交付](verification.md)。
