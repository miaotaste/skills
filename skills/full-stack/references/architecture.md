# 架构与技术选型

在新项目选型、划分应用与模块，或检查既有项目边界时阅读。以下是个人项目的默认组合；先核对产品需求和已有约束，再决定采用哪些部分。

## 先判断项目形态

- 先确认主要用户、首个完整操作、数据与文件规模，以及是否需要登录、公开页面、后台任务或机器调用。用这些需求解释选型，不为目录完整添加应用。
- 管理后台、个人工作台等交互为主的应用，默认采用独立 SPA 与 API。需要搜索引擎收录、服务端渲染或大量公开内容的项目，先评估 SSR/SSG；不直接套用纯 SPA。
- 既有项目优先沿用已验证的框架与组织方式。已有 Next.js 等全栈框架时，保留其路由、渲染和部署模型；可借用下面的业务边界，不默认拆出 Hono 或迁移到 Vite。
- 新增框架或升级版本前，检查目标项目的 manifest、锁文件、运行时要求与已安装文档，必要时查当前官方资料；Next.js 项目按其 `AGENTS.md` 阅读本地对应版本指南。本技能不固定依赖版本。

## 默认技术组合

| 范围 | 默认选择 | 适用理由与边界 |
| --- | --- | --- |
| 工程与语言 | TypeScript、Vite+、pnpm workspace/catalog | 多应用统一命令、依赖版本与锁文件；已有工具链不为使用技能而替换，单应用也不必拆成多个包 |
| 管理界面 | React、Ant Design | 表单、列表、弹窗等业务交互优先使用现成组件；品牌展示页按设计需求选型，不强制后台视觉 |
| 路由与数据 | TanStack Router、TanStack Query | SPA 路由与服务端数据缓存分工；用户草稿、临时 UI 状态不当成服务器缓存 |
| API | Node.js、Hono | 适合独立 HTTP 服务；已有框架的服务端能力足够时沿用它 |
| 数据与迁移 | PostgreSQL、Drizzle | 关系、约束与事务由数据库承担；ORM 与迁移工具版本配套，数据库实现在服务端内部 |
| 公共契约 | Zod 与推导出的 TypeScript 类型 | 在协议边界验证实际输入和响应；类型检查不能代替运行时校验 |

对新项目明确记录实际选用版本、运行时和包管理器，提交锁文件。共享依赖可以放 workspace catalog；不复制其他项目的整份依赖、别名、override 或构建许可。

## 应用与公共契约

- 多应用项目可用 `apps/admin`、`apps/server` 与 `packages/contracts` 起步；名称随产品职责调整。扩展端、公开站点和文档站只有需要时才建立。
- 应用通过 HTTP 等公开协议协作，不跨应用导入实现源码。共享包按实际职责建立，不要求只有一个共享包，也不提前建设通用组件平台。
- contracts 只包含跨应用需要的数据结构、校验和协议常量，不包含数据库连接、ORM 表模型、密钥、服务端存储实现或浏览器私有状态。
- HTTP 参数、错误状态和响应编码属于协议适配层；业务规则和操作顺序放在共用用例中。新增 MCP 等入口时复用这些用例，避免形成第二套业务行为。
- 公共响应显式选取允许公开的字段；数据库新增列不应自动进入 API。需要生成接口文档时，从契约和实际注册定义维护同一份事实来源。

## 服务端按业务组织

优先按产品能力划分 `modules/<业务>`，再按复杂度建立内部层次：

| 层或入口 | 职责 | 依赖约束 |
| --- | --- | --- |
| `domain` | 可独立表达与验证的业务规则 | 不依赖 HTTP、ORM、环境变量或具体外部服务 |
| `application` | 安排用例步骤，声明所需能力接口 | 依赖领域和显式接口；不创建连接或导入具体适配器 |
| `adapters` | 协议、持久化和第三方能力的接入 | 实现应用层接口，把技术结果转换为用例可理解的结果 |
| `infrastructure` | 数据库、对象存储、队列等通用实现 | 不反向依赖具体业务模块，也不决定页面展示与业务状态 |
| 装配与进程入口 | 读取配置，创建并连接实现，管理启停 | 具体依赖在这里汇合，资源按生命周期统一释放 |

- 简单 CRUD 可以只有应用用例和适配层；没有独立规则时不建立空的 `domain`，不强制每个模块目录齐全。
- `shared` 只放真正跨模块、职责稳定的接口或规则，不能反向依赖业务模块；单模块的错误、状态和展示策略留在所属模块。
- 跨模块写入通过显式能力接口协作，并使用同一事务绑定的实现；不在用例中重新从连接池取连接。跨模块只读查询可由专门查询适配器完成，避免服务相互调用形成环。
- 普通事务与需要幂等重放的业务变更分别处理；按实际并发编辑需求引入 revision，不为所有读写机械增加幂等记录或版本号。数据、迁移与恢复细节见 [开发流程](development.md)。

## 前端分工

新建管理端默认按层组织：`app` 装配路由、主题和 Provider；`pages` 协调页面；`components` 表达展示和交互；`hooks` 复用状态逻辑；`services` 处理协议；`utils` 保留纯函数。已有按功能组织的项目可保留原结构。

- 服务访问统一处理凭证、网络错误、HTTP 状态与响应校验；业务页面不直接拼装重复的请求约定。
- 查询缓存、编辑草稿和上传进度分别管理；保存后按实际影响更新或失效缓存。网络失败与并发冲突保留草稿，让用户有恢复入口。
- 重试策略区分读取与变更：读取可有限重试瞬时故障；写入只有具备明确幂等和恢复语义时才自动重试，不沿用查询默认值。
- Ant Design 组件按目标安装版本查询用法；主题集中配置，自定义样式消费 token。具体品牌色、圆角和版式由新项目决定。

## 按需求增加能力

| 能力 | 何时增加 | 需要保留的边界 |
| --- | --- | --- |
| MCP | Agent 需要发现并调用项目业务能力 | 与 HTTP 共用用例和校验；机器身份与浏览器会话分开，不能把无效机器凭证回退为 Cookie |
| pg-boss 队列 | 有耗时、可恢复或需后台执行的任务，且已使用 PostgreSQL | 业务记录与入队需要原子性时使用同一事务；明确重试、去重与停机行为，进程内或独立 worker 按负载决定 |
| 对象存储，默认可选 TOS | 需要长期保存用户文件或大文件直传 | 数据库记录业务身份，对象存储保存文件；临时签名 URL 不作为永久标识，文件操作不能假定随数据库回滚 |
| 浏览器扩展 | 需要网页采集或浏览器特有能力 | 独立应用通过公开 API 通信；后台管理凭证，离线队列收到确认后才清理 |
| FFmpeg / FFprobe 等媒体工具 | 需要媒体检查、转换或处理 | 明确子进程取消、超时和临时空间预算；保存成功与后处理成功分别表达 |
| VitePress | 项目说明已需要独立导航、搜索或多人维护 | 文档正文集中维护，README 保留入口；文档能独立构建，敏感配置不进入站点 |

部署环境、版本交付和恢复见 [部署](deployment.md)；验证边界和关键行为见 [验证](verification.md)。
