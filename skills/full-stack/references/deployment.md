# 部署与恢复

用于准备或实施云端发布，把本地可运行的应用变成可追溯、可更新、可恢复的服务。默认方案是火山引擎 ECS、托管 PostgreSQL、Docker Compose、Caddy、GitHub Actions 与 GHCR；需要永久文件时再加入 TOS。已有部署方案能满足需求时沿用，不为套用默认方案迁移基础设施。

## 确定部署边界

- 先确认本次是编写部署配置、准备发布，还是实际操作云资源。已有授权覆盖的步骤直接完成；只有缺少影响执行的目标、凭据或授权时才询问，不逐阶段重复确认。
- 创建收费资源、修改 DNS、执行生产迁移或发布前，以本次明确的目标环境和操作范围为依据。仅要求搭建项目或准备部署时，交付配置与操作步骤，不据此操作真实云环境。
- 默认采用单台 ECS 上独立运行 test、production 的低运维方案；两套环境都使用生产运行模式。可用性、数据隔离或资源竞争要求超出单机能力时，分主机或采用已有平台，保留下述产物与数据边界。
- 执行前按目标环境核对官方文档中的支持版本、地域、网络及权限要求。工具版本、服务器目录、域名、资源规格和容量都由当前项目确定，不从参考项目复制。

## 云端准备

| 资源 | 上线前落实的条件 |
| --- | --- |
| ECS 与网络 | 与数据库连通的私有网络、符合构建目标的 CPU 架构、Docker 与所需 Compose 能力、受控 SSH、网站入口端口；数据库和 Docker API 不直接暴露公网 |
| PostgreSQL | 环境各自的库和应用角色、跨库权限检查、备份策略与可用的恢复方式；日常应用角色不使用超级用户 |
| TOS（需要文件时） | 环境各自的 Bucket 和受限凭据；浏览器直传时配置对应 Origin 的 CORS；确认上传、读取和清理权限 |
| 域名与 HTTPS | 正确 DNS、可用的证书签发与续期链路；未启用的网络协议不添加对应解析 |
| GitHub 与 GHCR | 工作流权限、镜像包访问权限、部署环境配置、经核对的 SSH 主机密钥，以及 runner 到服务器的实际连通性 |

这里的配置文件只能证明准备了配置。真实网络、证书、仓库权限、对象存储权限和数据库备份需要分别取得验证结果；缺少条件时明确列为待办，不写成已经上线。

## 容器、入口与环境隔离

- 对默认 SPA + API 方案，构建两个运行镜像：Server 包含服务产物与必要运行依赖；Web 包含前端静态产物与 Caddy 配置。SSR 或既有全栈框架按其运行模型打包，不强拆成静态 Web。采用多阶段构建、锁文件安装、明确的运行时版本；服务进程使用非 root 用户。运行镜像不携带开发凭据、测试数据或无关源码。
- 公共 Caddy 入口负责 HTTPS 和按域名路由。对 SPA + API 方案，环境内 Web 提供 SPA，并把 API 与健康检查转发到 Server；SSR 应用则由框架运行服务处理页面请求，不套用 SPA 静态回退。应用服务不直接发布公网端口；公共入口配置独立维护，普通应用发布不顺带更新入口。
- 浏览器默认通过相对 API 路径同源访问。代理保留实际 Host、HTTPS 与鉴权信息，并限制可信代理来源；启用 MCP 等额外协议时再验证其必要请求头和连接行为。
- test 与 production 分别管理 Compose 项目、应用网络、持久卷、数据库、文件存储、会话与机器凭据、配置、锁和发布记录。一次 test 操作不能选择 production 的数据或恢复记录。
- 同机的公共入口、磁盘和系统仍是共同故障点；容器资源限制不能当成主机安全隔离。分别给应用分配 CPU、内存与临时空间预算，并为系统、镜像、日志和迁移留余量。
- 配置日志轮转和必要健康检查。停止服务时先停止接收新请求与领取任务，再等待或取消在途任务、释放资源，最后关闭数据库连接；停止宽限时间与任务行为匹配。

## 配置与凭据

- 区分构建配置和运行配置。前端构建变量会进入公开产物，不放密钥；环境切换优先依靠同源 API 和服务端运行配置，避免为 test、production 重建不同的前端镜像。
- 数据库、对象存储与服务鉴权配置在运行环境注入。只提交虚构值或占位符示例，私有文件设置受限权限；配置读取方式不得意外插值或截断密码、哈希中的特殊字符。
- GitHub 仅保存工作流确实需要的访问能力。拉取镜像优先使用短期、只读凭据；临时登录配置用完删除。业务凭据由服务器配置或既有密钥服务管理，不随发布包传输。
- 发布前检查必填配置、目标环境与数据库对应关系、容量及依赖是否满足要求；检查失败应在替换运行容器之前停止。可选能力未启用时，不伪装成已经可用。

## 构建与发布

发布入口默认手动触发；代码检查可接入现有 PR 或分支 CI。检查、构建、测试部署和生产发布各自的结果应可区分。

1. 固定本次源码提交，执行项目所需检查与测试，再构建并验证运行镜像。按 [验证与交付](verification.md) 选择真实数据库、浏览器和容器验收。
2. 推送镜像并记录不可变 digest。版本清单至少关联源码提交、镜像 digest 和对应部署配置；保留能恢复该版本的产物。
3. 将该版本部署到 test，记录目标环境、版本标识、执行结果与验收结果。测试部署不通过时先修复并生成新版本，不把失败结果视为验收。
4. 按已约定的人工验收与发布授权，将 test 通过的同一份镜像及版本化部署模板晋级到 production，注入 production 自己的配置与凭据。生产不重新构建，不用 `latest` 或当前分支头代替已验收版本，也不复制测试环境的私有配置。
5. 通过公网入口验证页面、API、健康状态和必要鉴权边界，成功后更新当前版本与历史发布记录；失败保留准确状态和日志。

同一环境的部署和数据库迁移共用执行锁，CI 不取消进行中的变更，服务器锁同时约束手动操作。两个环境可以分别操作，但仍需考虑共享资源。发布记录足够定位来源和恢复版本即可，不必先搭建复杂的产物证明系统。

## 迁移、初始化与回滚

- 生产顺序是备份 → 迁移 → 初始化 → 发布。迁移、seed 与启动如何分开见 [开发与数据](development.md)。
- 首次上线先在 test 检查并应用迁移、完成初始化，再部署和验收；production 使用同一版本，并按上一条顺序执行。
- 日常变更先在 test 验证升级与既有数据保留。production 应用迁移前确认可恢复的备份及停机需求；需要停机的迁移先停止相关写入或服务，不承诺默认零停机。
- 应用更新失败时，只恢复本环境原先运行且与当前数据库兼容的版本。没有可恢复版本或回退失败时，报告实际不可用状态，不宣称回滚成功。
- 应用回滚不会回退数据库。迁移失败不盲目重试；先检查实际迁移状态，再决定修复或恢复。迁移后旧应用不兼容时保持必要的维护状态，不能靠启动旧镜像解除。
- 数据库恢复是独立运维操作，需要明确恢复点与数据影响。测试恢复流程时使用隔离环境，不以备份任务存在代替恢复验证。

## 上线结果与后续运行

- 留下部署入口、目标环境、当前版本、验证结果，以及状态、日志、回滚和备份恢复的操作说明；敏感值不进入文档或日志。
- 按启用能力检查站点可用性、错误与后台任务状态、磁盘和资源用量、数据库备份、证书续期。只有实际配置并验证的监控才标为完成。
- 保留可回滚版本及其镜像、配置记录，清理策略与保留周期匹配。只清理明确可再生成或本次测试创建的资源，不能把业务数据库、文件桶、私有配置和持久卷当缓存。
- 交付时分别说明本地测试、CI、隔离容器与真实云端验证的结果和未执行项；不以其中一层通过推断其余层已验证。
